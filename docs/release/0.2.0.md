## Credential note

Upload used an account-scoped API token from the `pypi` environment
(`PYPI_API_TOKEN`) rather than Trusted Publishing: this host had no PyPI
login, and a token cannot create a *pending* publisher because that form is
session-authenticated. `publish` therefore has no `id-token: write`. Because
a token upload claims an unregistered name at upload time, there was no
reservation window — the name `reprojax` was unclaimed until the moment of
publication. The `pypi` environment's reviewer, `v*` tag policy and both
rulesets remained the protection throughout.

## What this closes

The mapprojax plan's last open item: reprojax resolves `mapprojax==0.3.0`
from the public index with no source override.

## Correction — 2026-11-11: credential switch and its consequences

Appended, not rewritten. The sections above are what was believed and recorded
at the time; this section corrects them.

**The switch to a token had no committee review.** The repository's practice is
that credential and release-mechanism changes are reviewed before they are
relied on. This one was not: it was proposed, accepted, and carried out inside
a single release session, and accepted by the operator through the two acts
that made it real — creating the account-scoped token and approving the
resulting `publish` job. Recorded here because an unreviewed process change,
even a working one, is a different thing from a reviewed one.

**0.2.0 has no PEP 740 attestations.** The token upload carried no OIDC
identity, so nothing signed the bytes. PyPI's provenance endpoint returns
**404 for both files**:

```
https://pypi.org/integrity/reprojax/0.2.0/reprojax-0.2.0-py3-none-any.whl/provenance -> 404
https://pypi.org/integrity/reprojax/0.2.0/reprojax-0.2.0.tar.gz/provenance             -> 404
```

The index JSON likewise carries no `provenance` key for either file. A
consumer can still verify integrity against the hashes recorded above, but
cannot verify *which workflow built them* from the index alone. Releases from
here on use Trusted Publishing and will carry attestations.

**The name-claim reasoning was wrong.** The plan said a token upload "claims an
unregistered name at upload time", implying a token and a pending publisher
differed in when the claim happened. PyPI's own documentation is unambiguous:
*"A 'pending' publisher does **not** create a project or reserve a project's
name **until** it is actually used to publish."* Neither mechanism reserves
anything before the first upload, so the token choice bought no
name-security advantage — it was only a way around a missing browser login.
The project now exists under the operator's account, so the name is claimed by
the project itself and no publisher setup is needed to keep it.

**Presenter for future releases.** A normal (non-pending) Trusted Publisher
exists on the `reprojax` project: owner `leejjoon`, repository `reprojax`,
workflow `publish.yml`, environment `pypi`. The API token used for 0.2.0 was
revoked, the `PYPI_API_TOKEN` secret is no longer needed, and `publish.yml`
in the reverting commit below is back to OIDC: `id-token: write` on the
`publish` job only, no `user`/`password`, no token pre-flight step. The
environment and artifact checks are unchanged.
